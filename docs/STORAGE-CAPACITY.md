# Storage Capacity — What Grows, How to Measure It, What Is Safe to Reclaim

A guide for any installation. It was written after a `/test` audit found an installation's root filesystem full;
that installation's own figures are kept outside the repository (a maintainer keeps them in a gitignored
`docs/local-*.md`). Paths below are the defaults: `${AUDIOBOOKS_VAR_DIR}` is `/var/lib/audiobooks` and
`${AUDIOBOOKS_HOME}` is `/opt/audiobooks` unless `/etc/audiobooks/audiobooks.conf` says otherwise.

## Consumers to Watch

| Path | What it holds | How it grows |
|------|---------------|--------------|
| `/var/lib/docker/` | Images, overlay2 layers, build cache, named volumes | Each image build and pull; volumes with the services that own them |
| `${AUDIOBOOKS_VAR_DIR}/streaming-audio/` | Translated WebM segments, per book and chapter | Linear with translation activity; no expiry today |
| `${AUDIOBOOKS_HOME}/` | Installed application code and venv | Stepwise, per release |
| `${AUDIOBOOKS_VAR_DIR}/db/` | SQLite databases | With library size and listening history |
| `${AUDIOBOOKS_VAR_DIR}/audible-venv/` | audible-cli virtual environment | Stepwise, per audible-cli update |
| `${AUDIOBOOKS_VAR_DIR}/backups/`, `auth.db.pre-upgrade-*` | Auth DB snapshots taken before schema migrations | One per migrating upgrade |

Measure, don't estimate:

```bash
sudo du -sh /var/lib/docker "${AUDIOBOOKS_VAR_DIR}"/* "${AUDIOBOOKS_HOME}" 2>/dev/null | sort -h
sudo docker system df          # images, containers, volumes, build cache — with the reclaimable share
df -h /                        # the filesystem they share
```

## Docker: Build Cache and Unused Images Are Reclaimable

Build cache and dangling or untagged images from earlier builds are safe to prune without affecting running
containers; `docker system df` shows how much of each is reclaimable:

```bash
sudo docker builder prune --keep-storage 1gb --force
sudo docker image prune -f     # keeps images used by running containers
```

**Do not prune volumes** — named volumes can hold other services' live data.

## Streaming-Audio Retention Policy (Proposed)

`${AUDIOBOOKS_VAR_DIR}/streaming-audio/` stores translated WebM audio segments generated by the stream-translate
worker. These accumulate permanently with no current expiry. Size it per book on your own installation:

```bash
sudo du -s "${AUDIOBOOKS_VAR_DIR}"/streaming-audio/* | awk '{n++; s+=$1} END {printf "%d books, %.1f MB per book\n", n, s/n/1024}'
```

**Proposed retention rule** (to be implemented in a future release):

Delete segments for a book when ALL of the following are true:

1. All chapters of that book have a completed `chapter_translations_audio` row
   (i.e., the full `chapter.webm` concatenation exists)
2. The book has not been accessed (no streaming playback) in the past **90 days**
3. The per-chapter `chapter.webm` files themselves are retained (safe to
   regenerate from segments, but regeneration costs GPU time)

Alternatively: keep only the per-chapter `chapter.webm` concatenations and delete
the constituent `seg*.webm` files once a chapter is complete. The player streams
from segments during live translation but falls back to `chapter.webm` on replay.

**Implementation location**: `library/backend/api_modular/maintenance_tasks/` —
a new `StreamingAudioCleanupTask` that runs as part of the maintenance scheduler.

**Manual interim cleanup** (operator discretion — deletes no chapter.webm):

```bash
# Preview what would be deleted: seg*.webm older than 90 days
sudo find "${AUDIOBOOKS_VAR_DIR:?}/streaming-audio/" -name "seg*.webm" -mtime +90 -type f | wc -l

# Actual deletion (confirm preview count first)
sudo find "${AUDIOBOOKS_VAR_DIR:?}/streaming-audio/" -name "seg*.webm" -mtime +90 -type f -delete
```

## Auth DB Upgrade Backups

`auth.db.pre-upgrade-*` files are created by `upgrade.sh` before each schema migration. They are safe to delete once
the upgrade is confirmed stable; keep the most recent:

```bash
# List all but the newest; review the list, then remove each by its full path
ls -t "${AUDIOBOOKS_VAR_DIR:?}"/auth.db.pre-upgrade-* | tail -n +2
```

## Capacity Planning

Docker data, application state and the installed application often share one filesystem. Watch:

- Docker images: stable if old images are pruned after each release
- `streaming-audio/`: linear with translation activity — measure the per-book figure above, multiply by the books
  you expect to translate
- Auth DB backups: one per migrating upgrade — cap at 3 retained copies

Before a release on a filling disk: `docker builder prune` + `docker image prune` reclaim space without touching
running services.
